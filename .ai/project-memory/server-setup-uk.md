# Сервер Birka: встановлення і щоденна робота

Для адміністратора, який ставить Birka на сервер і доглядає за ним. Рішення
власника 2026-10-11: інструкція українською для технічної людини, з точними
командами; перший запуск і щоденна робота. Оновлення до нової версії,
повернення на попередню, повне відновлення з резервної копії й безпека —
в англійській інструкції для розробника, [server-runbook.md](server-runbook.md)
і [backup-restore-runbook.md](backup-restore-runbook.md).

**Ця сторінка — переклад англійської інструкції.** Якщо вони десь
розходяться, правильна англійська: зміну в кроках встановлення роблять в
обох.

**Ще не виконано на справжньому сервері.** Кроки 3–10 відрепетирувано на
ноутбуці в Docker 2026-10-09 ([звіт](install-rehearsal-report.md)), без
Telegram.

## Що потрібно

| | |
|---|---|
| Сервер | Linux із Docker Engine і плагіном Compose. Для двох магазинів орієнтовно 2 vCPU, 2 ГБ RAM і 20 ГБ диска. Нічна перевірка відновлює повну копію бази поруч із нею, тож місця треба на дві бази. |
| Домен | DNS-запис `A` вказує на сервер; запису `AAAA` немає. Мережа compose не має IPv6, тож усі клієнти IPv6 дійшли б до API як одна адреса й ділили б один ліміт входів. Telegram відкриває застосунок лише через HTTPS; сертифікат Caddy отримує сам. |
| Відкриті порти | 22 (SSH) і 80 — TCP; 443 — і TCP, і UDP (UDP для HTTP/3). Більше нічого: база й API назовні не відкриті. Як закрити решту й пускати SSH лише за ключами — англійська інструкція, розділ «Security». |
| Годинник | синхронізований: `timedatectl` показує `System clock synchronized: yes`. Дані входу з Telegram із часом у майбутньому або старші за годину сервер не приймає. |
| Бот Telegram | створений через @BotFather. Його токен підписує кожен вхід; на сервері має бути той самий. |
| Ключ власника для копій (age) | створений на комп’ютері власника (крок 8, пункт 1). На сервер іде лише його відкрита частина. |
| Хто дізнається про проблеми | власник — через бота, і адміністратор — його номер у Telegram (рішення власника 2026-10-03). Адміністратора ще не названо. |
| Зовнішній сервіс перевірки | обліковий запис на ім’я власника, щоб помітити сервер, який зупинився повністю (крок 8a). |

Часовий пояс сервера — Київ, щоб нічна копія о 03:15 була ніччю для
магазинів:

```sh
sudo timedatectl set-timezone Europe/Kyiv
```

## Перше встановлення

### 1. Код

```sh
sudo mkdir -p /srv/birka && sudo chown "$USER" /srv/birka
git clone https://github.com/mainvuzol/birka.git /srv/birka
cd /srv/birka && git checkout <коміт релізу>
```

Ставте лише коміт, у якого пройшли всі перевірки CI.

Caddy читає `infra/Caddyfile` без прав root
([ADR-0017](../decisions/ADR-0017-what-a-container-may-do.md)), тож файл
має бути доступний для читання всім: `ls -l infra/Caddyfile` показує
`-rw-r--r--`; якщо ні — `chmod 644 infra/Caddyfile`.

### 2. Налаштування

```sh
cd /srv/birka/infra
cp .env.example .env && chmod 600 .env
```

У `.env`:

| | |
|---|---|
| `BIRKA_APP_ENV` | `production` (типове значення). Тоді API не запуститься без токена бота й секрету сесій щонайменше 32 байти і ховає свою документацію API. |
| `BIRKA_DOMAIN` | домен, наприклад `shop.example.com` |
| `POSTGRES_PASSWORD` | довгий і випадковий: `openssl rand -base64 32` |
| `BIRKA_APP_DB_PASSWORD` | ще один так само. API і `backup-watch` підключаються як `birka_app`, яка лише читає й пише рядки; міграції й копії робить власник бази — роль PostgreSQL із `POSTGRES_PASSWORD` вище ([ADR-0016](../decisions/ADR-0016-the-apps-database-role.md)) |
| `BIRKA_TELEGRAM_BOT_TOKEN` | від @BotFather |
| `BIRKA_SESSION_SECRET` | `openssl rand -base64 48` |
| `BIRKA_BACKUP_AGE_RECIPIENTS` | відкритий ключ власника, `age1…` |
| `BIRKA_ADMIN_TELEGRAM_IDS` | номер адміністратора в Telegram; кілька — через кому (крок 8a) |
| `BIRKA_HEARTBEAT_URL` | адреса перевірки зовнішнього сервісу (крок 8a). Хто її знає, може «відмічатися» замість сервера, тож вона лишається лише в `.env` |
| `BIRKA_SENTRY_DSN` | порожньо: подробиці помилок лишаються в журналі сервера (рішення власника 2026-10-03) |

**Збережіть копію `.env` у менеджері паролів.** Її немає в жодній
резервній копії.

### 3. Збирання і база

```sh
export BIRKA_RELEASE=$(git -C /srv/birka rev-parse --short HEAD)   # версія, яку називають застосунок і його помилки
docker compose build
docker compose --profile ops build ops
docker compose up -d --wait db
docker compose --profile ops run --rm --no-deps ops alembic upgrade head
docker compose --profile ops run --rm --no-deps ops alembic check     # "No new upgrade operations detected."
docker compose --profile ops run --rm --no-deps ops python -m scripts.app_role   # "birka_app: created", "… tables: read and write"
```

Міграції ніколи не запускаються самі, коли стартує API. Кожну запускає
людина з `ops` як власник бази (роль PostgreSQL, не власник магазину): роль
самого API не може змінювати схему.
`scripts.app_role` дає ролі `birka_app` пароль із `.env` і її права;
повторний запуск нічого не змінює.

### 4. Запуск

```sh
docker compose up -d
# Кілька секунд, поки стартує API, Caddy відповідає 502, а під час першого
# запуску відмовляє в з’єднанні, доки не має сертифіката: повторіть.
curl -fsS --retry 30 --retry-delay 2 --retry-all-errors https://<домен>/api/v1/health    # {"status":"ok","environment":"production"}
curl -fsS https://<домен>/api/v1/ready     # {"status":"ready"}: база відповідає і її схема актуальна
docker compose ps                          # api за хвилину-дві показує (healthy)
```

Якщо перший `curl` і далі падає з помилкою SSL, у Caddy ще немає
сертифіката: `docker compose logs caddy` скаже чому — зазвичай запис `A`
домену або закритий порт 80 чи 443.

`up -d` запускає п’ять служб: базу, API, `backup-watch`, Caddy і `web`.
`web` збирає застосунок у том Caddy і завершується — це єдиний контейнер,
який і має зупинитися.

### 5. Бот відкриває застосунок

У @BotFather:
1. Оберіть бота.
2. Bot Settings → Menu Button.
3. Вкажіть адресу кнопки `https://<домен>/`.

Відкрийте бота в Telegram і натисніть кнопку. Застосунок покаже «Доступу ще
немає» з номером Telegram цієї людини.

### 6. Власник і місця магазину

Власник відкриває застосунок, як у кроці 5, і передає номер, який той
показав. Тоді:

```sh
docker compose run --rm --no-deps api python -m scripts.seed_organization \
  --telegram-user-id <номер власника> --owner-name "<ім’я>" --org-name "<магазин>" \
  --main-name "<назва основного магазину>" --second-name "<назва другого магазину>"
```

Це створює:
- магазини `MAIN` і `SECOND` із вказаними назвами (типово «Основний
  магазин» і «Другий магазин»);
- один склад, спільний для обох магазинів;
- «Брак» кожного магазину;
- типові ролі;
- власника з роллю власника в кожному магазині.

Додайте `--with-child-warehouse`, якщо в другого магазину є свій склад. Він
приватний для `SECOND`: навіть власник має до нього доступ лише з роллю в
самому `SECOND` (`scripts.people grant … --store SECOND`, крок 7). Повторний
запуск безпечний: що вже є, лишається.

**Назву змінюють пізніше, за вказівкою власника:**

```sh
docker compose run --rm --no-deps api python -m scripts.stores rename \
  --approved-by <номер власника> --store MAIN --name "<нова назва>"
```

Власник натискає «Спробувати ще раз» — і входить.

### 7. Люди

Кожен продавець відкриває застосунок, як у кроці 5, і передає свій номер.
На слово власника:

```sh
docker compose run --rm --no-deps api python -m scripts.people grant \
  --approved-by <номер власника> --telegram-user-id <їхній номер> \
  --store MAIN --role SELLER
docker compose run --rm --no-deps api python -m scripts.people list
```

Як прибрати людину з магазину чи вимкнути в усіх магазинах — у
[звіті про людей](people-report.md).

**Загублений телефон** (рішення власника 2026-10-03): за вказівкою власника
завершіть усі входи цієї людини. Магазини й ролі лишаються; людина знову
відкриває застосунок на новому телефоні.

```sh
docker compose run --rm --no-deps api python -m scripts.people sign-out \
  --approved-by <номер власника> --telegram-user-id <їхній номер>
```

Хто тримає загублений телефон, ще може відкрити застосунок через Telegram
цієї людини: вона має також завершити сеанс того телефону в Telegram
(Налаштування → Пристрої). Вимкнення людини в усіх магазинах теж завершує
її входи, а пізніший `grant` старих не повертає.

### 8. Резервні копії

**1. Ключ власника — на комп’ютері власника:**

```sh
brew install age            # macOS; на Linux: apt install age
age-keygen -o birka-backup-key.txt
```

- Збережіть файл ключа в менеджері паролів, а ще роздрукуйте його або
  скопіюйте на флешку, що зберігається деінде. Без нього жодну копію не
  прочитати.
- Потім видаліть його з диска.
- Відкритий ключ (`age1…`, його друкує `age-keygen`) не секретний: він іде
  в `.env` сервера.

**2. На сервері** (у `.env` уже є `BIRKA_BACKUP_AGE_RECIPIENTS`):

```sh
cd /srv/birka/infra
mkdir -p backups && sudo chown 10001 backups       # користувач образу
docker compose --profile ops build ops             # знову після кожного оновлення
docker compose --profile ops run --rm ops          # перша ніч — вручну
cat backups/last-run.json                          # "ok": true
docker compose up -d backup-watch                  # разом із застосунком; `up -d` теж його запускає
docker compose run --rm backup-watch python -m scripts.backup_watch --status
```

Власник відкриває бота магазину в Telegram і один раз натискає «Start»,
щоб бот міг йому писати. Розділ «Резервні копії» показує, чи дійшло
останнє повідомлення.

Розклад — у crontab користувача root:

```
15 3 * * * cd /srv/birka/infra && docker compose --profile ops run --rm ops >> /var/log/birka-backup.log 2>&1
```

Журнал росте на кілька кілобайтів за ніч, тож його ротують щомісяця й
тримають рік, у `/etc/logrotate.d/birka-backup`:

```
/var/log/birka-backup.log {
    monthly
    rotate 12
    compress
    missingok
    notifempty
}
```

Ніч, яка застала попередню ще в роботі, другої копії поруч не робить:
записує невдалу ніч `still_running`, і власник дізнається про неї, як про
будь-яку невдалу. Кожен крок має обмеження часу, тож ніч, яка зависла,
теж закінчується як невдала.

**3. Доступ лише на читання для комп’ютера власника.** На сервері —
користувач, який може тільки читати теку копій (`rrsync` є в rsync 3.2.4 і
новіших):

```sh
sudo adduser --disabled-password --gecos "" birka-backup
sudo -u birka-backup mkdir -p ~birka-backup/.ssh
# Один рядок у ~birka-backup/.ssh/authorized_keys, з відкритим ключем машини власника:
command="rrsync -ro /srv/birka/infra/backups",restrict ssh-ed25519 AAAA… owner-nas
```

**4. Комп’ютер або NAS власника забирає копії:**

```sh
ssh-keygen -t ed25519 -f ~/.ssh/birka_backup -N ""      # його відкрита частина — у крок 3
BIRKA_BACKUP_SOURCE=birka-backup@shop.example.com: \
BIRKA_BACKUP_DEST="$HOME/birka-backups" \
sh infra/pull-backups.sh
```

Скрипт забирає лише зашифровані архіви з їхніми описами й звітами
перевірки, ніколи не перезаписує копію і звіряє кожен архів із
контрольною сумою сервера. Ночі, старші за 3 місяці, він видаляє (рішення
власника 2026-10-09), але завжди лишає найновішу цілу. Запускайте його
щодня, через кілька годин після нічної копії сервера: на macOS —
завданням launchd або в «Швидких командах», на NAS — його планувальником, на Linux
— cron.

Повідомлення скрипта:
- `NOT COLLECTED: rsync exited …` — сервер був недосяжний; наступний запуск
  забере пропущене.
- `DAMAGED OR MISSING: …dump.age` — архів не збігається з описом, і сам
  він більше не забирається. Видаліть файли тієї ночі тут (`birka-<час>.*`)
  і запустіть знову: архів заберуть ще раз, поки він є на сервері.

Копію, перенесену деінде вручну, власник видаляє сам: ім’я покупця, стерте
в застосунку, має зникнути з усіх копій за 3 місяці
([ADR-0015](../decisions/ADR-0015-customer-data-retention.md)).

**Реліз не завершено, доки розділ «Резервні копії» у власника не покаже
вдалу ніч.** Він під кнопкою «Ще», поруч із «Продаж», «Повернення», «Борги»
і «Каса»; «Ще ⚠» каже, що ніч чи сервер потребують власника.

### 8a. Як дізнатися, що щось зламалося

Рішення власника 2026-10-03
([ADR-0011](../decisions/ADR-0011-failures-are-visible.md)): `backup-watch`
дивиться щохвилини. Коли застосунок не відповідає 5 хвилин, диск майже
заповнений або ніхто не може увійти 10 хвилин, бот пише власнику й
адміністраторам із `BIRKA_ADMIN_TELEGRAM_IDS`. Один раз — коли проблема
почалася, раз на добу — поки триває, і раз — коли знову працює. З 9:00 до
20:00 за Києвом — зі звуком, в інший час — тихо. Розділ «Резервні копії»
показує ті самі проблеми.

Той самий наглядач тихо пише лише власнику мережі — ніколи не
адміністраторам — про **розбіжність у касі** під час закриття (не тим, хто
закривав касу; після причини або через 15 хвилин, повторюючи добу) і про
**завершену інвентаризацію складу** (не тим, хто її завершив). Це про
магазин, не про сервер. Окрім «Start» власника в боті, нічого
налаштовувати не треба.

1. **Адміністратор** відкриває бота магазину, натискає «Start», потім
   відкриває з нього застосунок: «Доступу ще немає» показує номер.
   Впишіть його в `BIRKA_ADMIN_TELEGRAM_IDS` і виконайте
   `docker compose up -d backup-watch`.
   `docker compose logs backup-watch | grep backup_watch.started` покаже,
   скільки адміністраторів він знає: частину налаштування, яка не є
   номером, пропускають, а не зупиняють наглядача.
2. **Зовнішній сервіс.** Сервер, який зупинився повністю, сам про це не
   скаже, тож власник заводить обліковий запис у сервісі, що чекає
   «відміток», наприклад Healthchecks.io або UptimeRobot:
   - **перевірка відміток** («heartbeat» або «cron job»): кожні 10 хвилин,
     10 хвилин запасу. Її адресу — у `BIRKA_HEARTBEAT_URL`, потім
     `docker compose up -d backup-watch`. Наглядач відмічається, лише поки
     дивиться, бот працює і є кому сказати, тож сервіс помітить і
     завислого наглядача, і відкликаний токен бота;
   - **перевірка адреси** `https://<домен>/api/v1/ready` кожні 5 хвилин,
     якщо сервіс таке має;
   - його сповіщення — в Telegram або на пошту власника.

   Сервіс дізнається лише адресу сайту і те, що сервер живий, — нічого про
   магазин.
3. **Перевірте, перш ніж магазини почнуть працювати:**
   ```sh
   docker compose stop api       # зачекайте 6 хвилин: бот скаже, що застосунок не відповідає
   docker compose start api      # за хвилину: знову працює
   docker compose stop backup-watch   # зачекайте 25 хвилин: зовнішній сервіс напише власнику
   docker compose start backup-watch
   ```

Що означає кожне повідомлення:

| Бот каже | Куди дивитися |
|---|---|
| сервер застосунку не відповідає | `docker compose ps` і `docker compose logs --since 15m api`: налаштування, з яким API не стартує, назване в останніх рядках |
| база не відповідає | `docker compose ps db`, `docker compose logs --since 15m db` і диск (`df -h /`). Якщо `docker compose logs --since 15m api` показує `InvalidPasswordError` або `InsufficientPrivilegeError` поруч із `database.unreachable`, база відповідає, але не пускає роль API: її немає (як після відновлення), у неї немає прав або пароль не той, що в `.env`. Тоді `docker compose --profile ops run --rm --no-deps ops python -m scripts.app_role` |
| база не оновлена для цієї версії | міграцію не запустили або вона впала: англійська інструкція, «A new version» |
| закінчується місце на диску | `docker system df`, потім `docker image prune -f && docker builder prune -f --filter until=720h`; тека копій; ніч, що падала, лишає всі копії |
| ніхто не може увійти — можливо, годинник | `timedatectl`: `System clock synchronized: yes` |
| ніхто не може увійти — можливо, токен бота | токен у `.env` проти @BotFather; після зміни — `docker compose up -d api backup-watch` |

### 9. Наявний товар магазинів — перш ніж щось рухати

**Нічого не приймають, не продають і не виправляють, доки цей крок не
зроблено.** Склад приймає початкові залишки лише тоді, коли в ньому ще
нічого не записано (рішення власника 2026-09-29). Перше приймання, продаж,
«фізично є» чи виправлення залишку закриває його для списку назавжди —
так само, як затверджений список: кожен склад приймає один список. Обидва
магазини продають зі спільного складу, тож одна поставка, прийнята там,
закриває шлях для всього, що магазини вже мають.

Порядок для кожного складу — у розділі 9 англійської інструкції; коротко:
1. **Підрахунок:** сфотографувати зошити й таблиці на один день; магазин
   далі продає на папері й зберігає ці продажі. Фото лишаються в магазині
   з тими назвами, під якими їх прочитав парсер.
2. **Файли:** парсер читає фото у файли формату Birka
   ([`formats/birka-stock-list/`](../../formats/birka-stock-list/README.md)),
   до 1 000 рядків у файлі. Кожен файл перевіряють перед тим, як віддати
   магазину, з теки `backend/` репозиторію, де встановлено його залежності:
   ```bash
   python -m scripts.check_stock_file FILE.json
   ```
   Він друкує `OK` із кількістю рядків і фото, інакше — кожну проблему з її
   рядком.
3. **Каталог:** кожну модель зі списку створюють у розділі «Каталог». Розміри
   створюйте до того, як відповідати рядкам за розмірами.
4. **Список:** власник або менеджер у розділі «Початкові залишки» →
   «Новий список» → склад → «Завантажити файл»; далі «Додати файл» і, для
   сторінки, яку парсер не прочитав, «Додати рядки вручну».
5. **Розбір:** кожен рядок — модель, розмір (або «Розмір невідомий»),
   звідки кількість, або «Це не товар» із причиною. Рядок із кількома
   розмірами дає по відповіді на кожен розмір.
6. **Затвердження:** власник затверджує список, і він стає залишком складу.
   Скасувати це не можна.
7. **Паперові продажі** з дня підрахунку вносять на касі як звичайні —
   лише після затвердження.
8. **Лише тоді** приймають нові поставки й продають у застосунку. Якщо з
   поставки, що прийшла після підрахунку, уже продавали на папері, спершу
   прийміть її, потім вносьте ці продажі — інакше каса не знайде товару.

Список — до 5 000 рядків і 5 000 відповідей (рішення власника 2026-10-08).
Найбільший склад магазинів — до 5 000 (власник, 2026-10-09). Якщо файли
складу все ж дають більше, зупиніться: спершу підіймають ліміт окремою
зміною. Поки список чекає, склад чекає теж: застосунок відмовляє в
прийманні, продажу й виправленні там, а магазини продають із нього на
папері.

### 10. Перевірка — нічого не вигадуючи

Усе, що записано на робочому сервері, справжнє, тож не перевіряйте
вигаданими продажами. Власник із телефона:
- входить і обирає магазин. Його адреса в `docker compose logs api` — це
  адреса телефона, а не `172.…`: ліміт входів рахує за нею;
- відкриває «Залишки» і бачить те, що сказав затверджений список, мінус
  внесені відтоді паперові продажі.

Далі перша справжня поставка перевіряє «Приймання», а перший справжній
продаж — касу.

## Щоденна робота

| | |
|---|---|
| Чи працює? | `docker compose ps` (api — `healthy`) і `curl -fsS https://<домен>/api/v1/ready`. `backup-watch` питає те саме щохвилини, і бот пише власнику та адміністраторам (крок 8a). |
| Журнал API | `docker compose logs --since 1h api`. Кожна служба тримає до 5 × 10 МБ. Запит пишеться без рядка параметрів, тож пошук боргу за іменем чи телефоном туди не потрапляє. Видно адресу продавця. Кожен рядок запиту має свій `request_id`. |
| «Номер запиту» від продавця | перші 8 символів `request_id`: `docker compose logs api \| grep <ці 8 символів>` знаходить запит і його помилку. |
| Зламаний екран | застосунок пише в журнал API `client.error`: який екран, яка помилка, версія й номер запиту, нічого про людину. `docker compose logs api \| grep client.error`. |
| Наглядач | `docker compose logs --since 1h backup-watch`. `backup_watch.server_trouble` — повідомлена проблема; `checked_in` / `check_in_withheld` — зовнішня відмітка; `bot_token_refused` — токен бота, який Telegram більше не приймає; `idempotency_purged` — щогодинне прибирання. |
| Минула нічна копія | `docker compose run --rm backup-watch python -m scripts.backup_watch --status` (код 0 лише якщо все гаразд). Власник бачить те саме в застосунку. |
| Диск | `df -h /`. База, ~10 копій на сервері й нічна тимчасова копія ділять його. Коли вільно менше 15 % або 3 ГБ, бот про це пише. Зі старими образами після оновлень — англійська інструкція, «A new version». |
| Помилки | у журналі API (рішення власника 2026-10-03: поки без Sentry). |
| Сертифікат сайту | `backup-watch` питає його в Caddy щоразу. За тиждень до закінчення власник отримує повідомлення бота, не частіше разу на добу. `backup_watch.certificate_unread` у журналі — нормально до першого сертифіката або поки Caddy перезапускається. |

**Ніколи не виконуйте `docker compose down -v`.** `-v` видаляє том бази, а
з ним усе, що записано після останньої нічної копії.

## Коли сервер не відповідає

Рішення власника 2026-10-04: магазини продають далі на папері й вносять
усе, коли сервер відповість
([ADR-0013](../decisions/ADR-0013-the-server-is-unreachable.md)).

**Що вже сталося, коли хтось на це дивиться:**
- За 5 хвилин бот написав власнику й адміністраторам: «⚠️ Сервер
  застосунку не відповідає. Продавці продають на папері.» Телефонувати
  нікому не треба.
- Телефони продавців показують «Сервер не відповідає. Продавайте на
  папері…», і магазини продають на папері, як каже їхня пам’ятка:
  [paper-when-the-server-is-down.md](paper-when-the-server-is-down.md).
- Телефон, чия операція не отримала відповіді, зберігає її й показує, з
  якого часу вона чекає; її рядок на папері позначено «у телефоні — <ім’я>».
- Коли сервер мертвий повністю, застосунок не відкривається взагалі. Про
  це скаже лише зовнішній сервіс (крок 8a, 2), якщо його налаштовано.
- Коли в одному магазині немає інтернету, застосунок там теж не
  відкривається, і ніхто не дізнається — навіть зовнішній сервіс: сервер
  відповідає решті. Продавець перевіряє інтернет магазину й, якщо його
  немає, каже менеджеру; магазин тим часом продає на папері (рішення
  власника 2026-10-08).

**Що перевіряє адміністратор**, у такому порядку:
1. `docker compose ps`: чи всі служби працюють, чи api `healthy`?
2. `curl -sS https://<домен>/api/v1/ready` ззовні: `ready` або причина —
   `database` чи `schema`. Без `-f`: на 503 він ховає тіло відповіді, а з
   ним і причину.
3. `docker compose logs --since 15m api` і `docker compose logs --since 15m db`.
   Запит, відхилений, бо база не відповіла, — рядок `request.unavailable`
   із `DATABASE` або `SCHEMA`: телефон отримав 503 і текст про папір, а не
   помилку з номером.
4. Диск: `df -h /`.
5. Далі таблиця з кроку 8a — за тим, що назвав бот.

**Коли сервер знову відповідає:**
- Бот пише «✅ Сервер знову відповідає: продажі з паперу можна вносити.» —
  власнику й адміністраторам, не магазинам: **скажіть магазинам** внести все
  з паперу до закриття каси (їхня пам’ятка, крок 6). Якщо сервер
  відповів до 6:00 тієї ж ночі, продавець спершу вносить усе з паперу,
  потім закриває касу; якщо ні — касу закривають наступного вечора
  (рішення власника 2026-10-07).
- **Відкрийте застосунок на кожному телефоні, що зберігає операцію.**
  Щойно в ньому оберуть магазин, телефон сам перевіряє її: «… підтверджено» (повернення:
  «Повернення оформлено») або «… не записано», і лише тоді її рядок
  вносять із паперу. Закритий телефон її тримає. Рядки загубленого
  телефона йдуть до менеджера, який перевіряє його продажі й повернення в
  розділі «Звіт», а внески за борги — у розділі «Борги», перш ніж вносити.
- **Магазин заблоковано або склад закрито, поки телефон зберігає там
  операцію** — операція лишається в телефоні для цього магазину, доки
  магазин знову не торгуватиме або склад не відкриють: сервер не приймає
  її повторно. Потім телефон перевірить її сам, щойно застосунок відкриють
  у цьому магазині, або кнопкою. В інших магазинах телефон працює.
- **Очікуйте пару**, якщо між продажем і його внесенням було закриття: продаж готівкою під час
  збою, внесений після закриття того дня, дає +X у тому закритті й −X у
  наступному, кожне з причиною «Продаж під час збою».
- **Продаж із паперу датовано днем внесення**, з позначкою «продано під
  час збою» в чеку, списку продажів і розділі «Звіт». Звіт за минулий день не
  змінюється.

## Чого тут немає

У [server-runbook.md](server-runbook.md) і
[backup-restore-runbook.md](backup-restore-runbook.md), англійською:
- **нова версія** — коли магазини зачинені, з копією перед оновленням;
- **повернення на попередню версію** — лише кодом, міграцією або з копії;
- **відновлення з резервної копії** — повне, на тому ж або новому сервері;
- **закріплена версія, змінена навмисно**, вимірювання на сервері й
  **безпека**.
