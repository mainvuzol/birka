### 3. P1 — API приймає каталогові ID чужої організації

Місця: [inventory.py:153](/Users/nikitahlushak/birka/backend/app/api/v1/inventory.py:153), [inventory/service.py:116](/Users/nikitahlushak/birka/backend/app/modules/inventory/service.py:116), [catalog/read.py:99](/Users/nikitahlushak/birka/backend/app/modules/catalog/read.py:99).

Приймання у власний магазин із variant і size іншої організації повертає **201** та записує зв’язки між організаціями. Продаж із власним variant, чужим size і корекцією також повертає **201**.

Це не демонстрація зміни залишків чужого магазину: проблема — використання чужого каталогу/розміру у власному магазині та порушення меж організацій. Потрібно перевіряти власника кожного variant, size, lot і store на спільному вході до критичних операцій; де доречно — підкріпити це складеними FK.

### 4. P1 — повторені рядки приймання втрачають закупівельну партію

Місце: [inventory.py:165](/Users/nikitahlushak/birka/backend/app/api/v1/inventory.py:165).

`lots[(variant_id, size_id)]` перезаписує попередню партію, якщо однаковий товар/розмір зустрічається двічі. При прийманні 2 одиниць по 100 грн і 3 одиниць по 200 грн обидва рухи посилаються на останню партію з ціною **200 грн**. Перша партія створена, але її рухи до неї не прив’язані. Це втрата походження закупівельної вартості, навіть якщо сумарний залишок правильний.

Потрібно зберігати відповідність кожного вхідного рядка його власній партії. Об’єднання рядків допустиме лише за явно однакових закупівельних фактів і визначених правил.

Доказ: `birka_m1b_api_review.py`: HTTP 201, однаковий `stock_lot_id` у двох результатах; БД повертає `[(2, 200.00), (3, 200.00)]` замість `[(2, 100.00), (3, 200.00)]`.

### 5. P2 — повтор бізнес-команди повертає 500

Місця: [sales.py:137](/Users/nikitahlushak/birka/backend/app/api/v1/sales.py:137), [sales/service.py:196](/Users/nikitahlushak/birka/backend/app/modules/sales/service.py:196).

Однаковий `command_id` із новим `Idempotency-Key` проходить кеш і намагається вставити другий Sale. UNIQUE правильно запобігає дублюванню, але необроблений IntegrityError перетворюється на **500**. Після очищення ідемпотентного кешу проблема має той самий механізм: клієнт не може отримати підтвердження вже виконаного продажу.

Потрібно повернути наявну операцію для того самого бізнес-запиту; зміна payload/магазину/актора повинна мати явно визначену безпечну поведінку, а не приховано повертати іншу операцію. Обробка повинна витримувати конкурентні вставки.

Доказ: `birka_m1b_api_review.py`: перший POST — **201**, повтор того самого тіла з іншим ключем — **500 Internal Server Error**. Дублікат продажу не створюється.

### 6. P2 — replay обходить актуальні дозволи продажу

Місце: [sales.py:133](/Users/nikitahlushak/birka/backend/app/api/v1/sales.py:133).

Replay повертається до виклику `create_sale`, де відбувається `scope.require`. Якщо користувач залишився активним членом організації, але втратив доступ до магазину/продажів, той самий запит з ключем повертає старий чек. Для того самого scope GET чека повертає **403**, а POST replay — **201**. Нове списання при цьому не виконується; дефект стосується актуального контролю доступу до відповіді.

Потрібно перевірити поточні дозволи та магазин перед будь-яким replay. Правило повторного отримання відповіді має бути узгоджене з правилами читання чеків.

Доказ: `birka_m1b_api_review.py`: `get_status=403`, `replay_status=201`, `same_receipt=true`.

### 7. P2 — продажі з корекціями можуть взаємно заблокуватись

Місця: [sales/service.py:201](/Users/nikitahlushak/birka/backend/app/modules/sales/service.py:201), [sales/service.py:225](/Users/nikitahlushak/birka/backend/app/modules/sales/service.py:225).

Кожен виклик `apply_movements` сортує рухи, але продаж викликає його окремо для корекцій і списань. Загальний порядок блокування порушується. За `A < B`, залишків `A=1, B=1`: T1 продає A1/B2 і коригує B+1; T2 продає A2/B1 і коригує A+1. T1 спершу блокує B, T2 — A; далі кожен чекає на іншого.

Відтворено **DeadlockDetectedError**: один продаж відкотився, другий закомітився. Потрібне єдине впорядковане блокування всього кошика до корекцій; політика повтору транзакції не замінює виправлення порядку.

Доказ: `birka_sale_review.py`, сценарій `DEADLOCK`, реальні окремі сесії PostgreSQL.

### 8. P2 — аудит корекції записує застарілий залишок «до»

Місце: [inventory.py:278](/Users/nikitahlushak/birka/backend/app/api/v1/inventory.py:278).

`before` читається до атомарної зміни. За початкового 10, конкурентного надходження +1 і власної корекції +1 фактичний перехід корекції — **11 → 12**, а відповідь та аудит записують **10 → 12**. Журнал помилково приписує цій операції зміни іншої транзакції.

Потрібно отримувати before з того самого атомарного результату: `quantity_after - quantity_delta`, або повертати обидва значення зі спільної захищеної операції.

Доказ: `birka_m1b_extra_review.py`: `actual_before=11`, `reported_before=10`, `reported_after=12`, `audit_before.quantity=10`.

### 9. P2 — історичний опис не зберігає всі ознаки варіанта

Місце: [catalog/read.py:87](/Users/nikitahlushak/birka/backend/app/modules/catalog/read.py:87).

Потрібно зберігати значення всіх ознак, важливих для ідентифікації на момент продажу, а не лише їхню поточну доступність через FK. Нове фото містить саме такі відмінності.

Доказ: `birka_m1b_extra_review.py`, різні texture на реальних рядках БД: `same_name=true`, `same_snapshot=true`.

- Попередній P1 щодо Sentry залишається: у `backend/app/main.py` усе ще немає вимкнення `include_local_variables`, scrubber очищує лише `event.request`. Витік раніше відтворено в цій розмові; цього разу повторний Sentry-прогін не виконувався.

- У чинному API немає створення товару каталогу; тестові товари створюються ORM-fixture. Тому повний користувацький шлях «створити товар → прийняти → продати» через API ще не продемонстрований. Відсутність M1C-парсера/матчера тут не вважається дефектом M1B.
- За відсутності Python lockfile backend-залежності резолвляться під час install; `pip install -e .[dev]` у CI досі не фіксує все дерево. Frontend lockfile та `npm ci` уже є.
- Прямі виклики сервісу з дробами більш ніж у дві десяткові позиції можуть мати неузгоджене округлення; чинний HTTP payload їх відхиляє. Це не включено до дев’яти відтворених HTTP/транзакційних дефектів.
